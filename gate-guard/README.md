# 水利闸门调度指令核验系统（gate-guard）

逐条校验闸门调度指令与上下游水位约束是否冲突；**任何一条硬性规则命中，直接阻断指令下发**，闸门状态不做任何改变，并写入阻断审计。

零依赖、零安装（仅需 Node.js ≥ 18），无数据库、无外部服务。

---

## 它解决什么

调度指令不能只看"闸门能不能动"，还要看**动了之后上下游会怎样**。本系统把一条指令与 12 条规则逐条对照：

- 指令本身合不合法（闸门存在、开度物理可达、水情数据没过期）；
- 上游让不让放（抗旱保水 / 防洪泄压）；
- 下游接不接得住（河道平衡水位、干渠暂态水位会不会漫顶）；
- 操作人有没有权限（大流量必须调度员）。

判定原则只有两条：

- **HARD（阻断）**：命中即拒绝下发。**没有任何角色、任何"强制"标志位可以绕过安全底线**；
- **SOFT（告警）**：不阻断，随指令回执返回并留痕（如泄洪闸高水头差的冲刷风险）。

## 核验规则

| 规则 | 核验内容 | 级别 | 判定逻辑 |
| --- | --- | --- | --- |
| R01 | 指令结构合法性 | HARD | 闸门/动作存在、参数非负、时长 1–1440 分钟、角色合法 |
| R02 | 遥测数据时效 | HARD | 上下游任一水位遥测超过 15 分钟，拒绝据此调度 |
| R03 | 开度物理范围 | HARD | 目标开度必须在 0..闸门最大开度内 |
| R04 | 单次操作变幅 | HARD | 本次变幅不得超过闸门 `maxStep`；**全关（紧急落闸）豁免** |
| R05 | 上游抗旱保水 | HARD | 上游低于保供水位（警戒水位 −2m）时禁止**加大**引水/泄放；关闸保水允许 |
| R06 | 上游防洪泄压 | HARD | 上游达到保证水位时禁止**减少**下泄（含关闭泄洪闸） |
| R07 | 下游河道稳态水位 | HARD/SOFT | 按全闸水账推演平衡水位：> 保证水位阻断，> 警戒水位告警 |
| R08 | 渠化河段暂态水位 | HARD/SOFT | 按指令作用时长做渠段水量平衡，推演峰位 > 保证/警戒 |
| R09 | 反向水头保护 | HARD | 下游水位 ≥ 上游时禁止增加开度（防倒灌） |
| R10 | 水头差防冲限制 | 按闸门配置 | 水头差超闸门允许值：G1/G2 阻断，G3 泄洪闸仅告警 |
| R11 | 出流能力 | HARD | 目标流量不得超过额定能力，也不得超过当前水头下的物理出流 |
| R12 | 大流量操作权限 | HARD | 目标流量 ≥ 闸门大流量阈值时，需要 `dispatcher` 及以上角色 |

### 水力学模型

- 闸孔出流（自由/淹没衔接连续的标准公式）：

  ```
  Q = Cd · b · a · √(2g · he)
  自由出流 he = h上游 − 堰顶；淹没出流 he = h上游 − h下游
  ```

- 河道平衡：`入流（外来 + 经闸）= 河段水位-出流曲线(平衡水位)`，二分反查平衡水位；
- 渠段暂态：`Δh = (入渠流量 − 渠尾出流) · 60 · 时长 / (水面面积)`；
- 推演基于**全闸水账**（例如开 G3 的旁路泄洪也计入 R_DOWN 平衡入流）。

### 河网拓扑

```
R_UP 上游河道站
 ├─ G1 进水闸 ──→ R_CANAL 北干渠 ── G2 节制闸 ──┐
 └─ G3 旁路泄洪闸 ─────────────────────────────→ R_DOWN 下游河道（城关段）
```

## HTTP API

| 方法/路径 | 作用 |
| --- | --- |
| `GET /health` | 健康检查 |
| `GET /api/state` | 当前各河段水情 + 闸门开度 |
| `GET /api/rules` | 规则清单与闸门/河段配置 |
| `POST /api/commands/check` | **预核验**（dry-run，不改变状态） |
| `POST /api/commands/dispatch` | 核验并下发；冲突返回 **409**，状态不变 |
| `POST /api/commands/dispatch-plan` | 批量顺序核验下发 |
| `GET /api/logs/accepted` | 已接受指令回执 |
| `GET /api/logs/blocked` | 被阻断指令审计（含命中规则与证据） |

指令体：

```json
{
  "gateId": "G1",
  "action": "SET_OPENING",     // SET_OPENING | SET_FLOW | SET_FULLY_OPEN | CLOSE
  "value": 0.9,                // SET_OPENING: 开度m；SET_FLOW: 目标流量 m³/s
  "durationMin": 60,
  "role": "operator"           // viewer | operator | dispatcher | admin
}
```

下发一条会漫渠的指令：

```bash
curl -X POST localhost:4100/api/commands/dispatch \
  -H 'content-type: application/json' \
  -d '{"gateId":"G3","action":"SET_OPENING","value":3.5,"durationMin":120,"role":"dispatcher"}'
# HTTP 409，violations 中给出 R07（下游平衡水位超保证水位）等全部命中规则与数值证据
```

### 批量语义

- 按顺序逐条核验，每条都基于"**实测水情 + 此前已接受指令叠加后的计划开度**"；
- 被阻断的指令不生效，不推进计划开度；
- `mode: "stop-on-block"`（默认）第一条阻断即停止，后续标记 `skipped`；`mode: "all"` 继续核验给出完整问题清单；
- 任一条被阻断，整批 `overall = rejected`。这使得"先开渠尾节制闸、再加大进水闸"这类**联合调度**可以通过，而单独下发后一条会被 R08 拦下。


## 设计取舍

- **判定逻辑只有一处**：HTTP、CLI、批量计划都走 `rules.js`，不存在"前端能过、后端被拦"的两套标准。
- **阻断必须给出证据**：每条命中规则都附实际值/阈值/推演值（如平衡水位、净入流、抬升幅度），供值班人员判断与审计回放。
- **告警不阻断、阻断不可绕过**：防洪场景下的冲刷风险（R10/G3）只告警留痕，避免把紧急操作也堵死；而漫顶、倒灌、超保证水位泄流这类硬底线没有强制开关。
- **水情与闸门状态分离**：遥测是外部事实，指令只推进"计划开度"，推演永远从实测水位出发，不把模型推算值当成新的"实测"。
